# Changelog

Release notes for the self-hosted install (`install/`), newest first. Each
release gets its own `## [vX.Y.Z]` section; changes that are not released yet
are collected under `## [Unreleased]`. (`HISTORY.md` is a different file: it
records where this directory came from.)

## [Unreleased]

### Added

- pipecat-manager gets `PIPECAT_CONFIG_ENCRYPTION_KEYS`, the master key for the platform keys it keeps in the database. `init.sh` generates it on install (`1:` plus the base64 of 32 random bytes, written to `.env` only), keeps an existing valid value when it rewrites `.env` (`--yes`, `--force-reinit`), generates an empty one, and keeps a malformed one with a warning; an `.env` that already has the earlier eight keys gets only the new one. Without a valid key the service still starts, but no stored platform key can be used (AI sessions that need one are rejected) and none can be stored.
- `sudo ./voipbin install`, `update all` and `update keys` also copy the platform keys of `.env` into pipecat-manager when they are not stored yet: `OPENAI_API_KEY`, `XAI_API_KEY`, `GOOGLE_API_KEY` (Gemini), `OPENROUTER_API_KEY`, `DEEPGRAM_API_KEY`, `CARTESIA_API_KEY`, `ELEVENLABS_API_KEY` and `LOCAL_LLM_ENDPOINTS` (one line of JSON, at most 2020 bytes; empty means off and nothing is stored). The step works like the one for the other services (standard input only, a stored key is never touched). `status` shows `OPENAI_API_KEY`, `GOOGLE_API_KEY` and `ELEVENLABS_API_KEY` as `set` only when every service that holds them has the key stored, and has a row for `LOCAL_LLM_ENDPOINTS`.
- number-manager gets `NUMBER_SECRET_ENCRYPTION_KEYS`, the master key for the provider secrets it keeps in the database. `init.sh` generates it on install (`1:` plus the base64 of 32 random bytes, written to `.env` only), keeps an existing valid value when it rewrites `.env` (`--yes`, `--force-reinit`), generates an empty one, and keeps a malformed one with a warning; an `.env` that already has the earlier seven keys gets only the new one. Without a valid key the service still starts, but no provider is usable and no provider secret can be stored.
- `sudo ./voipbin install`, `update all` and `update keys` also copy the Telnyx account of `.env` into number-manager: `TELNYX_API_KEY` as the secret of the `telnyx` provider (on standard input only) and `TELNYX_CONNECTION_ID` (required) and `TELNYX_PROFILE_ID` (optional) as its config, when that provider has no stored secret yet. A provider that has a stored secret is never touched, and a row whose connection id differs from `.env` is left alone with the commands to fix it. `update all` does it before the containers are recreated, so there is no gap. A Telnyx key without `TELNYX_CONNECTION_ID`, and any `TWILIO_*` value, cannot be stored from `.env` and are reported as a note (Twilio also needs a trunk SID and the account auth token: enter them with `number-control provider update` and `provider secret set`, see `README.md`); the note never fails a step. `sudo ./voipbin status` gets the rows `TELNYX_CONNECTION_ID (numbers)` and `TWILIO_SID + TWILIO_API_KEY` from the stored state.
- `sudo ./voipbin update keys [--check]`, and the same step inside `sudo ./voipbin install` (after the verification) and `sudo ./voipbin update all` (after the database migrations, before the containers are recreated): the provider keys that have a value in `.env` and are not stored yet are stored in the stored configs of ai-manager, email-manager, message-manager, transcribe-manager and tts-manager, from the new images in throwaway containers. Values travel on standard input only and are never printed; a key that is already stored is never touched, so the step is safe to repeat. A key whose stored value is unusable, or only one key of the AWS pair, is reported with the command that replaces it and left alone. `update all` stops before it changes any image (exit code 20, `stage=keys-preflight`) when a service with a key in `.env` is not given its master key, and before `up -d` (exit code 20, `stage=keys`) when storing fails; the running containers are untouched. `UPDATE_RESULT` gets a `keys=` field, and `status` shows a provider key as `set` (stored), `pending` (in `.env`, not stored yet), `incomplete` (one key of the AWS pair) or `empty`.
- timeline-manager now gets `DATABASE_DSN`, so its analysis store is initialized and the analysis endpoints are served, and it waits for the database to be healthy before starting.
- ai-manager gets `MCP_SECRET_ENCRYPTION_KEYS` and `ENGINE_BASE_KEY_ENCRYPTION_KEYS`, and `init.sh` generates both on install (a different random key each, written to `.env` only) and keeps existing valid values when it rewrites `.env` with `--yes` or `--force-reinit`. Without them ai-manager cannot store MCP server secrets or the API keys customers keep for their own LLM endpoints.
- ai-manager gets `AI_CONFIG_ENCRYPTION_KEYS` and email-manager gets `EMAIL_CONFIG_ENCRYPTION_KEYS`, the master keys for the secret values in their stored configs. `init.sh` generates them on install (a different random key each, written to `.env` only) and keeps existing valid values when it rewrites `.env`. Without a valid key the service still starts, but storing such a config secret fails.
- tts-manager gets `TTS_CONFIG_ENCRYPTION_KEYS`, transcribe-manager gets `TRANSCRIBE_CONFIG_ENCRYPTION_KEYS` and message-manager gets `MESSAGE_CONFIG_ENCRYPTION_KEYS`, the master keys for the secret values in their stored configs. `init.sh` generates them on install (a different random key each, written to `.env` only), keeps existing valid values when it rewrites `.env`, and on an `.env` that already has the earlier keys adds only the missing ones. Without a valid key the service still starts, but storing such a config secret fails.
- `LOCAL_LLM_MODELS` (ai-manager, pipecat-manager) and `LOCAL_LLM_ENDPOINTS` (stored for pipecat-manager, see the entries above) for self-hosted OpenAI-compatible LLM servers. Both are off by default; `.env.template` explains the format and the order to enable them.
- pipecat-script-runner now receives `GOOGLE_APPLICATION_CREDENTIALS` and the credentials file mount, like the other services that use Google APIs. The default is the dummy file `init.sh` creates, which is not a valid credential; set the variable in `.env` to a real service account file to use Google speech services.
- `sudo ./voipbin install`: a guided install that runs host checks, `init.sh`, `setup-host.sh` (after showing the host changes and asking), `start.sh`, a health verification and the first admin account in one command, and ends with the admin console URL and a one-time random password. `--yes --admin-email <e> --admin-password-file <path>` runs it without questions, the last line is `VOIPBIN_INSTALL: status=ok|error ...`, and `--resume` continues an install that stopped after the configuration step. `sudo ./voipbin` on a new checkout offers it.
- `scripts/create-admin.sh` creates or resets a customer's admin login (password from an environment variable, never on a command line) and sets its billing plan to unlimited. The dev seed now uses it too.
- `sudo ./voipbin` on a terminal now opens a start screen: a header with the install state, mode and directory, an input box between two rules, and a status bar (`Env`, `Services`, `DNS`, `Net`, `Mode`) refreshed after commands that change or report the state. Slash commands `/help`, `/install`, `/status`, `/start`, `/stop`, `/restart`, `/logs`, `/doctor`, `/update`, `/version`, `/clear` and `/exit` run the matching commands, and Tab completes them. The plain words keep working. Pipes, scripts, `NO_COLOR`, `TERM=dumb` and non-UTF-8 terminals keep the previous prompt and output, and commands run with arguments are unchanged.

### Changed

- The pinned pipecat-manager image (and its pipecat-script-runner sidecar) is updated to the build that reads the platform keys of AI voice sessions from the database only (`pipecat_configs`, `pipecat-control config list|set|clear`); it no longer reads `OPENAI_API_KEY`, `XAI_API_KEY`, `GOOGLE_API_KEY`, `OPENROUTER_API_KEY`, `DEEPGRAM_API_KEY`, `CARTESIA_API_KEY`, `ELEVENLABS_API_KEY` or `LOCAL_LLM_ENDPOINTS` from the environment, and a session that needs a key that is not stored is rejected. pipecat-script-runner no longer receives any platform key; those lines stay in `docker-compose.yml.dist` on pipecat-manager only as the values `update keys` copies from, and `LOCAL_LLM_ENDPOINTS` has an empty default now. A rotated key is used by the next session with no restart. `OPENAI_API_KEY`, `GOOGLE_API_KEY` and `ELEVENLABS_API_KEY` are stored separately for ai-manager or tts-manager and for pipecat-manager: rotate each (`pipecat-control config set`).
- The pinned number-manager image is updated to the build that reads its provider credentials (secret and connection id) from the database only; it no longer reads `TELNYX_*` or `TWILIO_*` from the environment, and `provider secret delete` does not go back to the environment. Number purchase, search and release need the stored Telnyx secret and connection id. The five `TWILIO_*`/`TELNYX_*` lines stay in `docker-compose.yml.dist` only as the values `update keys` copies from and for a rollback to an older image. `TELNYX_API_KEY` is stored separately by message-manager and number-manager: rotate it in both (`message-control config set`, `number-control provider secret set`) or with the admin API; a change in `.env` alone reaches neither.
- The pinned images of ai-manager, email-manager, message-manager, transcribe-manager, tts-manager and api-manager are updated to builds that include the stored configs (new `ai_configs`, `email_configs`, `message_configs`, `transcribe_configs` and `tts_configs` tables with their `_histories` tables, created when the services or `update all` first run them). The other services keep their current images, so the stack runs a mix of image versions until their pins are updated.
- The provider keys of ai-manager (`OPENAI_API_KEY`, `GOOGLE_API_KEY`), email-manager (`SENDGRID_API_KEY`, `MAILGUN_API_KEY`), message-manager (`MESSAGEBIRD_API_KEY`, `TELNYX_API_KEY`), transcribe-manager and tts-manager (`AWS_ACCESS_KEY`, `AWS_SECRET_KEY`) and tts-manager (`ELEVENLABS_API_KEY`) are now read from the services' stored configs only; the new images ignore the matching environment variables. `.env` is where you enter a key the first time. A key that is already stored is never replaced from `.env`, so a change in `.env` alone does not reach it: rotate it with `<service>-control config set` (value on standard input) or the admin API. `config clear` now removes the key instead of falling back to the environment; a value still in `.env` is stored again by the next `update all` or `update keys`. `GOOGLE_API_KEY`, `ELEVENLABS_API_KEY` and `OPENAI_API_KEY` are also read from `.env` by pipecat, so replace them in both places.
- The new email-manager image processes a Mailgun webhook only when its signature matches `MAILGUN_WEBHOOK_SIGNING_KEY` (or the stored `mailgun.webhook_signing_key`). Until one of them is set, Mailgun delivery-status webhooks are rejected and the email status stays unchanged. `.env.template` and the compose file do not carry `MAILGUN_WEBHOOK_SIGNING_KEY` yet; store the key from the Mailgun account inside the email-manager container with `email-control config set --key mailgun.webhook_signing_key --actor-id <uuid>` (the value is read from stdin; the command needs `EMAIL_CONFIG_ENCRYPTION_KEYS`). A webhook rejected before the key is stored is not retried, so that email keeps its status.
- `sudo ./voipbin init` passes its options to `init.sh`, and `init`, `start` and `clean` now exit with a non-zero code when they fail.
- `sudo ./voipbin clean --volumes|--images|--purge|--all` lists what it removes and asks for `yes` first; scripts must add `--force`. `clean --purge` now also removes `docker-compose.yml`, `versions.lock` and the install marker, like `scripts/clean.sh --purge`. When `clean --volumes` keeps the VoIP network interfaces, `clean` and `scripts/clean.sh` say to remove them (`--network`) before installing again, and `install` stops at the host check while they are still there: a new install next to them loses container network access.
- `check-install.sh`, `doctor.sh` and the install verification treat an "unhealthy" container whose image has no healthcheck binary as a known non-fault, and tts-manager restarting because no TTS credentials are configured as an optional feature that is not set up. Other unhealthy, restarting or exited containers still fail.
- `sudo ./voipbin start` no longer resolves image tags on installs with `versions.lock`, whose images are already pinned by digest.
- `help` and `--help` show the same grouped command list (resource commands moved to `help api`), and `help`, `--help` and `version` work without sudo. Output has no color when `NO_COLOR` is set or stdout is not a terminal.
- `status` shows which optional provider keys are set and no longer prints MySQL or RabbitMQ credentials; the start summary no longer prints the RabbitMQ password.
- User-facing text no longer calls the install a sandbox, and `.env.template` labels secrets and certificates as generated and provider keys as optional. New installs use `voipbin-placeholder` for the GCP placeholder values; existing `.env` values keep working.
- The start screen header is now pinned to the top of the terminal, like a title bar: a compact six-line VoIPBin phone icon drawn with quadrant and half blocks with the install state, mode and directory beside it stays in place while command output and the input box scroll below it, and `/clear` clears only the part below. Terminals narrower than 60 columns or shorter than 14 rows show the three info lines once at the start, as before. If a terminal is ever left with a scroll region (the CLI was killed), run `reset`.

### Removed

- Removed the unused legacy host-alembic helpers (`configure_alembic`, `run_migrations`) from `init_database.sh`. The installer already ran only the asterisk migration stream through `scripts/migrate.sh`; the services create the `bin_manager` schema themselves.

### Fixed

- `doctor.sh` no longer warns that `start.sh` will re-seed test data on an install that has the dev seed off (the default). Without `VOIPBIN_SANDBOX_DEV_SEED=true` in `.env` the missing `.test_data_initialized` marker is expected, so the `test-data` check now passes there. With the seed on it still warns.
- The icon in the start screen header is now a complete phone shape instead of a block that looked cut off.
- `sudo ./voipbin` on a terminal no longer keeps running at 100% CPU after its terminal is closed (a closed terminal window, a killed `tmux` session, a dropped SSH connection) when Python's `readline` is the libedit build. It now exits, also when it is waiting at a question of the guided install.

### Upgrade notes

- pipecat-manager: before `sudo ./voipbin update all`, add `PIPECAT_CONFIG_ENCRYPTION_KEYS` to `.env` and to the pipecat-manager entry of your live `docker-compose.yml`, add the `GOOGLE_API_KEY`, `OPENROUTER_API_KEY` and `LOCAL_LLM_ENDPOINTS` lines to pipecat-manager and remove the platform key lines (including `LOCAL_LLM_ENDPOINTS`) from pipecat-script-runner (the steps are in `README.md` under "Adopting the encryption keys, local LLM and timeline analysis settings", now with nine keys). `update all` stops before it changes any image (exit code 20, `stage=keys-preflight`) while the key is missing and a platform key is in `.env`, and otherwise stores the platform keys of `.env` in pipecat-manager before the containers are recreated. A platform key that is not stored is not used by the new image: check with `sudo ./voipbin status` that each key you use shows `set`.
- number-manager: add `NUMBER_SECRET_ENCRYPTION_KEYS` to `.env` and to the number-manager entry of your live `docker-compose.yml` before `sudo ./voipbin update all` (the steps are in `README.md` under "Adopting the encryption keys, local LLM and timeline analysis settings", now with eight keys). If `.env` has `TELNYX_API_KEY` and `TELNYX_CONNECTION_ID`, `update all` stops before it changes any image (exit code 20, `stage=keys-preflight`) while the key is missing, and otherwise stores the Telnyx account in number-manager before the containers are recreated. Without `TELNYX_CONNECTION_ID` in `.env` Telnyx cannot be stored, so number search, release and update stop working after the update: put the connection id of your Telnyx account in `.env` and run `sudo ./voipbin update keys`. Telnyx used for SMS only is not affected. Check with `sudo ./voipbin status` that `TELNYX_CONNECTION_ID (numbers)` shows `set`. Twilio is not read any more (the previous image could not use Twilio anyway).
- Your live `docker-compose.yml` is not updated by `git pull`. Merge the new settings by hand and add the encryption keys to `.env` (nine with number-manager's and pipecat-manager's) before `sudo ./voipbin update all`, which also moves your `docker-compose.yml` to the new ai-manager, email-manager, message-manager, transcribe-manager, tts-manager and api-manager images and stores the provider keys of `.env` in those services (without the master keys it stops with exit code 20 before it changes an image); the steps are in `README.md` under "Adopting the encryption keys, local LLM and timeline analysis settings". Do not run `init.sh --yes` or `--force-reinit` for this: they regenerate the database and RabbitMQ passwords.
- Until the merge, nothing else changes: the five services cannot store the secrets above and timeline-manager serves no analysis endpoints.
- After `update all`, the five services and pipecat-manager read their provider keys from the database only. Check with `sudo ./voipbin status` that each key you use shows `set`; after that, rotate keys with `<service>-control config set` or the admin API, not in `.env`. If you roll back to an older image, that image reads the environment again, so keep `.env` and the database in step.
- Back up `.env`. A lost encryption key cannot be recovered, and whatever was stored under it has to be entered again.
- Scripts that call `sudo ./voipbin clean --volumes`, `--images`, `--purge` or `--all` must add `--force`; without it (and without a terminal to answer `yes`) `clean` now removes nothing and exits with code 1.
