# VOIP-1339: Komodo 웹 UI 컨테이너 관리 도입 설계 (v5)

## v5 변경 요약 (4라운드 리뷰 반영)

4라운드에서 security-reviewer/architect 둘 다 **Approve**였다. security-reviewer가
블로킹은 아니지만 "놓치면 4번 항목(코드 레벨 강제)이 무력화된다"고 짚은 3가지를
반영: (1) `COMPOSE`에 `-f docker-compose.yml` 추가해 `COMPOSE_FILE` 환경변수
홀도 함께 차단, (2) `restart`/`logs`의 `"${2:-}"` → `"${@:2}"`로 정정(서비스명
생략 시 빈 문자열 인자 버그), (3) 테스트 10번에 긍정 단언(`komodo.sh` 안에
`-p komodo`가 실제로 있음)을 추가해 래퍼 자체가 나중에 `-p komodo`를 잃어도
부정 단언만으로는 못 잡는 구멍을 막음.

## v4 변경 요약 (3라운드 리뷰 반영)

3라운드에서 security-reviewer는 **Approve**, architect는 **Request Changes**(1건)였다.
architect의 지적: "`name: komodo` + 모든 실행 경로가 `-p komodo`를 쓴다"는 완화책이
실제로는 README 문서 한 곳에만 있고, `init-komodo.sh`는 compose를 호출조차 하지
않으며(사용법만 출력), 이를 강제하는 회귀 테스트도 없어 실효성이 문서 수준에
머문다는 것. v4는 이를 반영해 다음을 추가한다.

1. **`install/komodo/scripts/komodo.sh` 래퍼 스크립트 신설.** `init|up|down|restart|
   logs|ps|status` 서브커맨드를 제공하고, 내부적으로 항상 `docker compose -p komodo
   ...`를 호출한다 - `-p` 플래그는 compose 우선순위 최상위이므로 셸에
   `COMPOSE_PROJECT_NAME`이 export되어 있어도 이 래퍼를 통하면 항상 `komodo`
   프로젝트로 격리된다. README는 이제 raw `docker compose` 명령을 전혀 노출하지
   않고 이 래퍼만 안내한다.
2. **가드 추가 (defense-in-depth)**: `common.sh`의 `check_compose_profiles_conflict()`와
   동일한 패턴으로, `komodo.sh`가 `COMPOSE_PROJECT_NAME`이 export되어 있고
   `komodo`가 아니면 raw `docker compose` 명령을 직접 실행하려는 운영자에게
   경고를 남기도록 README에 "래퍼를 쓰지 않고 직접 `docker compose` 명령을 쓸
   경우 반드시 `-p komodo`를 붙이거나 `unset COMPOSE_PROJECT_NAME`" 문구를 명시한다.
3. **`tests/config.bats`에 회귀 테스트 추가** (10번 항목): `install/komodo/README.md`와
   `install/komodo/scripts/`에 `-p komodo`(또는 `komodo.sh` 래퍼 호출) 없이 bare한
   `docker compose up`/`down` 문자열이 없는지 grep으로 고정.
4. **periphery healthcheck 제거 근거를 실측 명령/결과로 보강**: "정확한 원인은
   미상"이라고만 적었던 부분에 실제 실행한 명령과 결과를 명시 (아래 "실측 검증"
   갱신).
5. **`versions.lock` 파이프라인 미편입 결정에 후속 티켓 번호 명기**: [VOIP-1340](https://voipbin.atlassian.net/browse/VOIP-1340)
6. **`install/komodo/.env`도 `.gitignore` 재사용 대상임을 테스트 계획에 명시** (9번 항목 보강).

## v3 변경 요약 (2라운드 리뷰 반영)

2라운드에서도 security-reviewer/architect 둘 다 Request Changes였으나, 두 리뷰 모두
"핵심 아키텍처 결정(별도 프로젝트 분리, Stack 미생성, digest pin, 실측 healthcheck)은
1라운드 지적을 구조적으로 해소했다"고 인정했고, 남은 지적은 문서 정정 + 마무리 디테일
수준이었다. v3는 그 지적 전부를 반영했고, **핵심 시나리오를 실제로 처음부터(빈 볼륨)
로컬에서 재현해 검증**했다.

1. **`COMPOSE_PROJECT_NAME` export 시 프로젝트 격리가 깨지는 문제 (architect #1, 최고
   심각도)**: 이 저장소 `README.md`가 운영자에게 `export COMPOSE_PROJECT_NAME=sandbox`를
   셸 프로파일에 넣도록 권장하고 있고(`derive_compose_project_name()`, `common.sh:748-751`),
   compose 스펙의 프로젝트명 우선순위는 `-p` 플래그 > `COMPOSE_PROJECT_NAME` 환경변수 >
   compose 파일의 최상위 `name:` 키 > 디렉토리명 순서다. 즉 **`name:` 필드만으로는
   export된 환경변수를 이길 수 없다.** → `install/komodo/docker-compose.yml.dist`에
   `name: komodo`를 넣어 두되(환경변수가 없는 경우의 기본값으로 유효), **모든 실행
   경로(README 명령어, `init-komodo.sh`)가 `docker compose -p komodo ...`를 명시적으로
   써서 환경변수 유무와 무관하게 프로젝트를 고정**한다. 아래 "실측 검증" 항목에서
   `name: komodo` + 별도 디렉토리 조합으로 실제 격리된 브리지 네트워크가 생성됨을
   확인했다.
2. **`docker-compose.yml.dist` → 실사용 파일 복사 경로 누락 (security-reviewer #B,
   architect #2)**: 메인 스택과 동일한 copy-once 패턴을 `init-komodo.sh`에도 적용한다
   (`.dist`를 최초 1회만 `docker-compose.yml`로 복사, 이후 git-ignore, 재실행 시
   덮어쓰지 않음) — `install/.gitignore`가 하위 디렉토리에도 적용되므로 별도 gitignore
   규칙 추가 불필요, 실제 패턴만 재사용.
3. **시크릿 생성 함수 위치 오류 정정 (security-reviewer #A)**: `generate_random_key`는
   `common.sh`가 아니라 `install/scripts/init.sh:568-570`에 정의되어 있음을 실측
   확인(`openssl rand -hex 32` 두 줄짜리 함수). 메인 `init.sh`를 건드리지 않기 위해
   `common.sh`로 옮기지 않고, **`init-komodo.sh`에 동일한 두 줄을 명시적으로 복제**하고
   "재사용이 아니라 의도적 복제"라고 주석에 남긴다 (최소 변경 원칙 - 메인 설치 경로에
   손대지 않음).
4. **공개키 환경변수명 출처 인용 (architect #3)**: `KOMODO_PERIPHERY_PUBLIC_KEY`,
   `PERIPHERY_CORE_PUBLIC_KEYS`는 상류 공식 `compose.env`(moghtech/komodo main 브랜치,
   raw 파일 직접 fetch로 확인, "Allow Periphery to connect via generated public key"
   / "Use the public key generated by Core." 섹션)에 실재하는 변수명이며, 아래 "실측
   검증"에서 이 두 변수로 core/periphery 키 교환이 실제로 성공함을 라이브 로그로
   확인했다(`CoreConfig { periphery_public_keys: Some(["file:/config/keys/periphery.pub"]) ... }`,
   에러 없이 부팅).
5. **빈 볼륨 콜드 부팅 전체 체인 실측 검증 (architect #3)**: `mongo→core→periphery`를
   `condition: service_healthy` 체인으로 빈 볼륨부터 로컬에서 직접 기동해 키 부트스트랩
   교착이 없음을 확인했다 (아래 "실측 검증" 참고). 이전 라운드의 "Connection refused"는
   `depends_on`에 healthcheck 조건이 없던 임시 테스트 설정의 문제였고, `service_healthy`
   조건을 넣은 정식 구성에서는 재현되지 않았다.
6. **periphery healthcheck을 v3에서 제거 (실측 결과 반영, 신규 발견)**: 2라운드 문서가
   "미검증"이라고 명시했던 `wget --no-check-certificate` 기반 periphery healthcheck를
   실제로 빈 볼륨부터 끝까지 기동해 검증한 결과, **컨테이너는 정상 동작하는데도
   healthcheck는 계속 `unhealthy`로 보고됨을 확인했다** (자체 TLS 자체서명 인증서에 대한
   `wget --no-check-certificate`가 이 이미지에서 예상대로 동작하지 않음 - 정확한 원인은
   미상). 동작하지 않는 것으로 실증된 healthcheck를 그대로 남기면 이 저장소가 VOIP-1336
   redis-exporter에서 이미 겪은 "영구 unhealthy" 문제를 스스로 재현하는 것이므로,
   **v3는 periphery에 healthcheck를 아예 넣지 않는다.** (기능 자체는 정상 - core/mongo
   에는 정상 동작하는 healthcheck가 있어 이 두 개로 콜드 부팅 순서는 여전히 보장됨.
   periphery 전용 헬스체크 방법은 follow-up.)
7. **digest pin 표기를 저장소 관례(`tag@sha256:...`)로 정정**: `mongo:7@sha256:...`,
   `ghcr.io/moghtech/komodo-core:2@sha256:...`, `ghcr.io/moghtech/komodo-periphery:2@sha256:...`
   (기존 v2는 태그 없이 digest만 사용 - VOIP-1336 섹션의 실제 표기와 불일치했음).
8. **`container_name` 접두사를 `voipbin-komodo-*` → `komodo-*`로 변경** (별도 스택임을
   이름에서도 명확히, architect should-fix 반영).
9. **`tests/config.bats` 대응 계획 명시** (기존엔 누락 - 아래 "테스트 계획" 절 신설).
10. **`docker-compose.test.yml`/`versions.lock` 대응 여부를 명시적으로 "해당 없음"으로
    결정하고 근거를 남김** (아래 "범위 밖" 절).

## 실측 검증 (v3, 로컬 재현)

빈 볼륨 상태에서 아래 compose로 `mongo → core(service_healthy) → periphery(service_healthy)`
전체 체인을 3회 반복 기동해 확인:

```yaml
name: komodo-verify
services:
  mongo: {image: "mongo:7@sha256:be3d6353...", healthcheck: mongosh ping, ...}
  core:
    image: "ghcr.io/moghtech/komodo-core:2@sha256:7ae1d154..."
    depends_on: {mongo: {condition: service_healthy}}
    healthcheck: {test: ["CMD","curl","-sf","-o","/dev/null","http://127.0.0.1:9120/version"]}
  periphery:
    image: "ghcr.io/moghtech/komodo-periphery:2@sha256:639e0197..."
    depends_on: {core: {condition: service_healthy}}
    # healthcheck 없음 (v3 변경사항 #6)
```

결과:
- `mongo`, `core` 모두 `healthy`로 정상 전이. `core` 로그에 `Server starting on
  http://[::]:9120` 확인.
- `periphery`는 core가 healthy가 된 후에만 기동되고(콜드 부팅 교착 없음), 자체 키를
  `/config/keys/periphery.{key,pub}`에 생성한 뒤 `ws://core:9120/ws/periphery?server=...`로
  **에러 없이** outbound 연결을 개시함 (이전 라운드의 "Connection refused"가
  재현되지 않음 - `depends_on` 조건 누락이 원인이었음이 확인됨).
- `docker network ls` / `docker inspect`로 `komodo-verify_default`라는 별도 브리지
  네트워크가 생성됨을 확인 (메인 스택 네트워크와 완전히 분리).
- 3개 이미지의 실제 digest: `mongo:7` →
  `sha256:be3d6353f3ea3fd3d22e016d19da20fcd6937eda0739eb6d2aeed335baa60f90`,
  `komodo-core:2` → `sha256:7ae1d1547b16f1fd88902050105d80bbefc41b3023baf1f6dbc2b8df47ecb526`
  (`Komodo Core version: v2.3.2`), `komodo-periphery:2` →
  `sha256:639e019751642518a0fbdc2720e5f39789e76aa495a499852b9585ffacf71149` (`v2.3.2`).
- `komodo-core` 이미지에는 `curl`만 있고 `wget`이 없음(실측). `komodo-periphery`는
  반대로 `wget`만 있고 `curl`/`pgrep`/`ps`가 없음(실측).
- `/auth/options`는 존재하지 않는 경로(SPA 캐치올, 200 아닌 404 + HTML 응답)이고,
  `/version`은 실제 API 엔드포인트로 `200`을 반환함을 확인 → core healthcheck는
  `/version` 사용.
- 테스트 완료 후 `docker compose down -v`로 정리, 이 저장소에는 어떤 흔적도 남지 않음.
- **periphery healthcheck 디버그 (v4 추가, 정직하게 기록)**: 실측 재현에서
  `komodo-verify-periphery-1` 컨테이너 자체는 로그상 정상 기동(자체 키 생성,
  core로 outbound 연결 개시, 에러 없음)했음에도 `docker compose ps`가 계속
  `unhealthy`로 보고했고(healthcheck `test`에 넣은 `wget --no-check-certificate
  -q -O /dev/null https://127.0.0.1:8120/; c=$$?; [ $$c -eq 0 -o $$c -eq 8 ]`
  구문이 실제로 `retries: 5` 윈도우 안에서 성공 판정을 받지 못함) 자체는
  컨테이너 상태(`docker compose ps` 출력)로 직접 확인했다. **다만 원인을 밝히기
  위한 `docker exec` 대화형 디버깅까지는 이번 조사에서 수행하지 않았다** -
  이 문서의 이전 버전이 "정확한 원인 미상"이라고 쓴 것은 그 의미다(추측성
  원인 서술을 새로 지어내지 않는다). 컨테이너는 정상, healthcheck 판정 로직만
  신뢰할 수 없다는 사실 자체는 `docker compose ps`로 직접 관측했으므로, healthcheck를
  제거하는 결정의 근거로는 충분하다고 판단했다. 정확한 원인 규명(TLS/응답
  포맷/타임아웃 중 무엇인지)은 follow-up으로 남긴다.

## v3 설계

### 디렉토리 구조

```
install/komodo/
├── docker-compose.yml.dist   # `name: komodo` 최상위 필드 포함, 별도 프로젝트
├── .env.template
├── scripts/
│   ├── init-komodo.sh         # .env + docker-compose.yml 생성 (멱등, copy-once)
│   └── komodo.sh               # 래퍼: init|up|down|restart|logs|ps|status (v4 신설)
└── README.md
```

기존 `install/docker-compose.yml.dist`, `.env.template`, `scripts/init.sh`,
`scripts/common.sh`는 **일절 수정하지 않는다**.

### `install/komodo/docker-compose.yml.dist`

```yaml
# Komodo - 웹 UI 컨테이너 관리 (VOIP-1339). voipbin 메인 스택과 완전히 별도의
# compose 프로젝트다.
#
# name: komodo (최상위 필드) - 프로젝트명의 기본값을 명시적으로 고정한다. 단,
# compose의 프로젝트명 결정 우선순위는 `-p` 플래그 > COMPOSE_PROJECT_NAME 환경
# 변수 > 이 name 필드 > 디렉토리명 순서라서, 이 필드만으로는 이 저장소의
# README가 권장하는 `export COMPOSE_PROJECT_NAME=sandbox`(메인 스택용) 셸
# 프로파일 설정을 이기지 못한다. 그래서 이 스택을 다루는 모든 명령은 반드시
# `docker compose -p komodo ...`로 프로젝트를 명시한다 (README/init-komodo.sh
# 전부 이 규칙을 따름) - 셸 환경과 무관하게 항상 격리를 보장하기 위함.
# 격리가 깨지면 이 스택이 메인 voipbin 네트워크(10.100.0.0/16, 30개 이상 컨테이너)
# 에 합류하게 되고, periphery의 docker.sock(=host-root-equivalent) 접근이 그
# 네트워크의 아무 컨테이너에나 노출된다 - 이 프로젝트명 고정이 격리의 핵심
# 방어선이다.
name: komodo

x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  mongo:
    image: mongo:7@sha256:be3d6353f3ea3fd3d22e016d19da20fcd6937eda0739eb6d2aeed335baa60f90
    container_name: komodo-mongo
    restart: always
    logging: *default-logging
    labels:
      komodo.skip:
    command: ["--quiet", "--wiredTigerCacheSizeGB", "0.25"]
    environment:
      - MONGO_INITDB_ROOT_USERNAME=${KOMODO_DATABASE_USERNAME:?run scripts/init-komodo.sh first}
      - MONGO_INITDB_ROOT_PASSWORD=${KOMODO_DATABASE_PASSWORD:?run scripts/init-komodo.sh first}
    volumes:
      - komodo_mongo_data:/data/db
      - komodo_mongo_config:/data/configdb
    healthcheck:
      test: ["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping')"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 20s

  core:
    image: ghcr.io/moghtech/komodo-core:2@sha256:7ae1d1547b16f1fd88902050105d80bbefc41b3023baf1f6dbc2b8df47ecb526
    container_name: komodo-core
    init: true
    restart: always
    logging: *default-logging
    labels:
      komodo.skip:
    depends_on:
      mongo:
        condition: service_healthy
```

### `install/komodo/scripts/komodo.sh` (신설, v4)

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")/.."   # install/komodo/

# 이 스크립트가 유일한 정식 실행 경로 - 항상 -p komodo를 명시해 프로젝트를
# 고정한다 (`-p` 플래그는 compose 프로젝트명 결정에서 최우선순위이므로,
# 셸에 COMPOSE_PROJECT_NAME이 export되어 있어도(README가 메인 스택용으로
# 권장하는 `export COMPOSE_PROJECT_NAME=sandbox` 포함) 이 스크립트를 통하면
# 항상 komodo 프로젝트로 격리된다). README는 raw `docker compose` 명령을
# 안내하지 않고 이 스크립트만 안내한다.
COMPOSE="docker compose -p komodo -f docker-compose.yml"

# defense-in-depth: 그럼에도 raw docker compose를 직접 쓰려는 운영자를 위해
# 경고만 남긴다 (강제는 -p 플래그 자체가 하므로 이 체크는 진단용).
if [[ -n "${COMPOSE_PROJECT_NAME:-}" && "${COMPOSE_PROJECT_NAME}" != "komodo" ]]; then
    echo "[komodo] Note: \$COMPOSE_PROJECT_NAME=${COMPOSE_PROJECT_NAME} is set in your shell." >&2
    echo "[komodo] This script always uses -p komodo regardless, but if you run" >&2
    echo "[komodo] 'docker compose' directly in this directory, add -p komodo" >&2
    echo "[komodo] yourself or 'unset COMPOSE_PROJECT_NAME' first." >&2
fi

case "${1:-}" in
    init)   ./scripts/init-komodo.sh ;;
    up)     $COMPOSE up -d ;;
    down)   $COMPOSE down ;;
    restart) $COMPOSE restart "${@:2}" ;;
    logs)   $COMPOSE logs -f "${@:2}" ;;
    ps)     $COMPOSE ps ;;
    status) $COMPOSE ps ;;
    *) echo "Usage: $0 {init|up|down|restart [service]|logs [service]|ps|status}" >&2; exit 1 ;;
esac
```

### `install/komodo/README.md` (개요, 본문은 구현 시 작성)

- 시작: `cd install/komodo && ./scripts/komodo.sh init && ./scripts/komodo.sh up`
- 접속: `ssh -L 9120:127.0.0.1:9120 root@<host>` 후 `http://localhost:9120`
- **역할 분담**: 메트릭/대시보드는 Grafana(VOIP-1336), 컨테이너 재시작/로그
  확인/수동 조작은 Komodo. 두 도구는 목적이 다르며 서로 대체하지 않는다.
- **포함**: 컨테이너 목록/재시작/중지/시작/로그/리소스(CPU/메모리/네트워크) 확인
- **포함 안 됨 (하지 말 것)**: Stack/Deploy 기능으로 voipbin 메인 스택을
  배포/재배포하지 말 것. 배포는 CircleCI→SSH가 유일한 정식 경로. Stack
  리소스를 만들지 않았으므로 이 기능은 UI에 없음.
- 중지: `./scripts/komodo.sh down` (메인 스택과 완전히 독립된 프로젝트라
  `stop.sh`/`clean.sh`는 이 스택에 영향 없음, 역방향도 마찬가지)
- **`docker compose`를 직접 쓰지 말고 이 래퍼(`komodo.sh`)를 통해서만 조작할 것.**
  래퍼가 항상 `-p komodo`를 강제해 프로젝트 격리를 보장한다 (메인 스택의
  `export COMPOSE_PROJECT_NAME=sandbox` 셸 프로파일 설정이 있어도 무관). 부득이
  raw `docker compose`를 써야 한다면 반드시 `-p komodo`를 직접 붙이거나
  `unset COMPOSE_PROJECT_NAME` 후 실행할 것 - 그러지 않으면 이 스택이 메인
  voipbin 네트워크에 합류해 `komodo-periphery`의 `docker.sock` 접근이 30여 개
  컨테이너에 노출된다.
- 이미지 digest 갱신은 `versions.lock`/`sync-compose-images.sh` 파이프라인에
  포함되지 않음([VOIP-1340](https://voipbin.atlassian.net/browse/VOIP-1340)
  후속 검토) - `docker-compose.yml.dist`를 직접 diff해 수동 갱신

### 리스크 및 완화 (v3, 최종)

| 리스크 | 완화 |
|---|---|
| `docker.sock` 마운트 = 호스트 컨테이너 전체에 대한 사실상 root 권한 | 127.0.0.1 바인딩(core) + SSH 터널 + 기존 nftables + core/periphery 키 페어 인증 + 프로젝트명 고정(`-p komodo`)에 의한 네트워크 격리(실측 확인) |
| `COMPOSE_PROJECT_NAME` 환경변수가 export되어 있으면 프로젝트 격리가 깨질 수 있음 | 모든 실행 경로(README, init-komodo.sh)가 `-p komodo`를 명시적으로 사용 - 환경변수 유무와 무관하게 격리 보장 |
| Komodo가 배포 경로를 CI와 이중화 | 1차 스코프에서 Stack 리소스를 아예 만들지 않음 - Deploy/Destroy UI 자체가 존재하지 않음 |
| Komodo UI에서 실수로 자기 자신을 중지 | 3개 서비스 모두 `komodo.skip:` 라벨 (상류 공식 관례) |
| voipbin 메인 스택의 `stop.sh --clean`이 Komodo 데이터까지 삭제 | 별도 compose 프로젝트+디렉토리로 완전 분리, 메인 스택 lifecycle과 무관 |
| 이미지 공급망 리스크 (특히 제3자 moghtech 이미지) | 3개 이미지 모두 실측 digest pin, 저장소 관례(`tag@sha256:`)와 표기 일치 |
| healthcheck 바이너리 부재로 영구 unhealthy (VOIP-1336 redis-exporter 전례) | core/mongo는 실측으로 동작 확인된 healthcheck 적용, periphery는 동작하지 않는 healthcheck를 실측으로 확인 후 아예 제거(follow-up으로 남김) - "확인 안 하고 그럴듯하게 넣기"를 하지 않음 |
| bm-nyc-01처럼 이미 설치된 서버에 시크릿이 채워지지 않아 무인증 기동 | compose `:?` 필수 변수 검증으로 값 누락 시 `docker compose up` 자체가 즉시 에러 (fail-fast, 조용한 무인증 기동 불가) |
| 콜드 부팅 시 core/periphery 키 부트스트랩 교착 | 빈 볼륨부터 실측 재현 - 교착 없음 확인 |
| MongoDB 컨테이너 자체 노출 | 호스트 포트 미게시(내부 전용), 기존 postgres/clickhouse와 동일 원칙 |

  인프라)과 성격이 다름. digest 갱신은 당분간 `docker-compose.yml.dist`

  `docker compose -p voipbin-test -f docker-compose.yml -f
  docker-compose.test.yml`로 **메인 스택 프로젝트만** 다루고, Komodo는 별도
  프로젝트(`-p komodo`)라 이 통합 테스트의 대상이 되지 않음. 컨테이너 이름도
  `komodo-*`로 메인 스택과 겹치지 않아 이름 충돌 회피를 위한 `!reset` 오버라이드도
  불필요
- periphery의 정확한 헬스체크 방법 (TLS 자체서명 처리 포함) — v3에서 healthcheck
  자체를 제거했으므로 이 항목이 후속 과제로 남음
