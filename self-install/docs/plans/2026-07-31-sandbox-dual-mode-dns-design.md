# Sandbox Dual-Mode DNS: Internal Demo and Real-Domain Production Install

- **Date:** 2026-07-31
- **Ticket:** VOIP-1275
- **Status:** APPROVED (design review: rounds 1–2 Request Changes, rounds 3–4 Approve; rev 4 applies round 4's non-blocking suggestions)
- **Predecessors:** `2026-07-30-sandbox-install-reliability-design.md` (public-DNS runbook gap, sudo-gated verification), `2026-07-31-sandbox-full-service-parity-design.md` (48-service baseline), `2026-07-05-production-grade-horizontal-scale-design.md` (Track B gap inventory: TLS lifecycle, public DNS)

## 0. Goal

One sandbox codebase that supports two install modes, selected at init time, with zero regression to the current demo experience:

- **Mode `internal` (default):** today's behavior, unchanged. CoreDNS serves `*.voipbin.test`, `/etc/resolv.conf` forwarding, mkcert/self-signed certs, `sudo ./scripts/start.sh` one-command flow.
- **Mode `external`:** operator supplies a real domain (e.g. `example.com`) with public/corporate DNS A-records they manage. CoreDNS and the resolv.conf hijack are not deployed. TLS uses real-CA certificates (BYO, with a documented Let's Encrypt recipe). All domain-dependent values derive from the supplied base domain.

Cross-cutting: both modes must be installable end-to-end by an AI agent, with root-requiring steps isolated into a single documented command and machine-parseable success/failure output at every stage.

## 1. Current state (facts the design must respect)

Reconnaissance of `main` (`ea38d0c`) established:

1. **No domain templating exists.** `voipbin.test` appears as independent literals in `.env.template` (11 vars), the `init.sh` heredoc, `docker-compose.yml` `${VAR:-default}` fallbacks, `common.sh`, `setup-dns.sh`, `start.sh`, `voipbin-cli.py` (30+ sites), `test_call.py`, `softphone.py`. `BASE_DOMAIN`/`BASE_HOSTNAME` exist but nothing composes the other values from them.
2. **Four active clobber sites would destroy or corrupt an external-mode install:**
   - `common.sh:188-189` `update_env_ips()` rewrites `API_URL`/`WEBSOCKET_URL` back to `api.voipbin.test:8443` on every host-IP change (invoked from `start.sh`, `setup-dns.sh`, `setup-voip-network.sh`).
   - `start.sh:135-145` (issuer check) + `start.sh:149` (`rm -rf certs/`) delete and regenerate `certs/` with mkcert whenever the api cert's issuer does not contain `mkcert` — i.e. it would destroy any real-CA certificate on every start.
   - `setup-voip-network.sh:136-154` calls `update_env_ips` → `regenerate_ssl_certs` → an unconditional `generate_coredns_config` (line 150) on any IP change; it runs in both modes (§2.5), so all three inner calls need mode/TLS gates.
   - `start.sh:648-656` (Step 7) calls `generate_coredns_config` unconditionally on **every** start (no IP-change condition), rewriting the Corefile with `.test` zones; `start.sh:661-668` (Step 8) then invokes `setup-dns.sh -y` with internal-mode messaging. Both need mode gates, not just downstream no-ops.
3. **Cert consumption (verified by image probe, not inferred):** the kamailio image's entrypoint runs `generate_defines.py`, which substitutes the literal `BASE_DOMAIN` placeholder in `/templates/tls.cfg` and `kamailio.cfg` with the `BASE_DOMAIN` env var at container start; the resulting TLS config reads `/certs/registrar.<BASE_DOMAIN>/fullchain.pem`, `/certs/conference.<BASE_DOMAIN>/...`, `/certs/sip-service.<BASE_DOMAIN>/...` etc. So kamailio's cert layout is exactly `certs/<name>.<domain>/{fullchain,privkey}.pem`, driven at runtime by env — a domain change needs no image change. api-manager and hook-manager consume the api cert as base64 env strings (`API_SSL_*`, `HOOK_SSL_*`) written into `.env`. No renewal mechanism exists.
4. **CoreDNS** is an always-started compose service (`voipbin-dns`) binding host port 53 (localhost + LAN IP); the Corefile is generated by `common.sh:generate_coredns_config()` (untracked artifact). Web names (`api.`, `admin.`, `meet.`, `talk.`) resolve to `HOST_EXTERNAL_IP`; a catch-all zone resolves everything else (`sip.`, `conference.`, `trunk.`, `pstn.`, `*.registrar.`, ...) to `KAMAILIO_EXTERNAL_IP`.
5. **Root gating is whole-script:** `init.sh` and `start.sh` both hard-require `$EUID == 0`. The actual root-requiring operations are only: mkcert package install + `mkcert -install` (trust-store), resolv.conf replacement, and `setup-voip-network.sh` (macvlan interfaces). Everything else (writing `.env`, generating certs with mkcert, Corefile generation, `docker compose` with docker-group membership, DB init, test customer) is unprivileged. The untracked `init_no_sudo.sh` is an ad-hoc precedent, not a supported path.
6. **SIP realms are state:** registrar-manager composes `{customer_id}.{DOMAIN_NAME_EXTENSION}` at extension-creation time and persists it in the `asterisk` DB. Changing the domain later requires deleting and recreating extensions via the API; there is no in-place migration.
7. **Existing verification:** `check-env-template-sync.sh` compares `.env.template` against the `init.sh` heredoc (both directions; its extractor only sees `^VAR=` lines *inside* the `cat > "$ENV_FILE" << EOF` heredoc — a constraint §2.1 must respect). `sync-compose-images.sh` is domain-agnostic. `start.sh`'s "N/M services" is a running-container count, not a health assertion; real health polling exists only in `voipbin-cli.py:_verify_stack`. The bats suite (126 tests) asserts on hardcoded `voipbin.test` strings in generated Corefile output and script source.
8. **The test harness already models "no host mutation" as a compose profile** (`docker-compose.test.yml` puts coredns/kamailio/rtpengine/asterisk-* behind `profiles: ["host-mutating"]`).
9. **Frontend domain values are runtime-injected (verified by image probe):** the `square-*` images' CMD runs `env.sh`, which regenerates `/usr/share/nginx/html/env-config.js` (`window._env_`) from `REACT_APP_*` env vars at every container start. Combined with fact 3, both previously-assumed consumers are confirmed runtime-configurable: a domain change is `.env` edit + container recreate, never an image rebuild, and external mode requires **no monorepo changes**.
10. `scripts/generate-certs.sh` is dead code (no caller anywhere; defaults to `voipbin.net`; emits a file set nothing consumes). It is deleted in this cycle to avoid a second, drifting cert path (§2.6 `install-certs.sh` supersedes it).

## 2. Design

### 2.1 Mode model and single source of truth

Two new `.env` variables, written by `init.sh` and documented in `.env.template`:

```
DOMAIN_MODE=internal          # internal | external
COMPOSE_PROFILES=internal-dns # internal mode; external mode writes the key with an empty value
TLS_MODE=mkcert               # mkcert | selfsigned | byo
```

(`COMPOSE_PROFILES` is always emitted, empty in external mode — Compose treats empty as "no profiles", and a symmetric key set keeps `check-env-template-sync.sh` trivially satisfied in both modes.)

A single derivation function in `common.sh` becomes the only place domain values are composed:

```bash
# derive_domain_env <base_domain>
# Prints the 11 domain-dependent env values for the given base domain.
API_URL=https://api.<d>:8443/
WEBSOCKET_URL=wss://api.<d>:8443/v1.0/ws
REGISTRAR_URL=wss://sip.<d>:5066
REGISTRAR_DOMAIN=registrar.<d>
CONFERENCE_URL=wss://conference.<d>
CONFERENCE_DOMAIN=conference.<d>
DOMAIN_NAME_EXTENSION=registrar.<d>
DOMAIN_NAME_TRUNK=trunk.<d>
EMAIL_VERIFY_BASE_URL=https://api.<d>:8443
BASE_DOMAIN=<d>
BASE_HOSTNAME=<d>
```

`init.sh` always derives, in both modes. For `<d> = voipbin.test` the derived values are byte-identical to today's literals, which is how mode `internal` stays unchanged while the code path is shared (no separate template to drift).

**Sync-checker compatibility (explicit resolution):** `check-env-template-sync.sh`'s extractor only sees `^VAR=` lines inside the `init.sh` heredoc (§1.7). Therefore `derive_domain_env` sets shell variables *before* the heredoc, and the heredoc keeps one literal line per var in the form `API_URL=$DERIVED_API_URL`, `REGISTRAR_DOMAIN=$DERIVED_REGISTRAR_DOMAIN`, etc. The extractor's `^[A-Z0-9_]+=` match still sees all 11 names; the checker needs no changes.

Port 8443 stays in both modes this cycle (moving external mode to 443 changes the api-manager port mapping and every URL; deferred as a follow-up, recorded in §7).

`docker-compose.yml` `${VAR:-voipbin.test...}` fallback defaults stay as they are: they are only reached when `.env` is missing a var, which the sync checker prevents. Not touching them keeps the compose diff minimal.

### 2.2 `init.sh` CLI contract (non-interactive, machine-parseable)

`init.sh` gains a flag parser, invoked from inside `main()` (not at top level — `tests/test_helper.bash:332` sources `init.sh` with only the `main "$@"` call stripped, so top-level parsing would execute in every bats test). No flags → exactly today's interactive behavior (internal mode, overwrite prompt).

```
./scripts/init.sh [--mode internal|external] [--domain <base-domain>]
                  [--tls mkcert|selfsigned|byo] [--cert <fullchain.pem> --key <privkey.pem>]
                  [--yes] [--force-reinit]
```

- `--mode external` requires `--domain`. `--domain` with `--mode internal` is rejected (internal is `voipbin.test` by definition; a vanity internal domain is out of scope).
- `--mode external` requires `--tls byo` + `--cert`/`--key` (see §2.6). mkcert/selfsigned are rejected in external mode with a pointer to the runbook.
- `--yes` answers all prompts (today only the `.env` overwrite prompt); with `--yes` and an existing compatible `.env`, init is idempotent-refresh (same semantics as answering `y` today).
- Domain validation: lowercase RFC-1123 labels, at least two labels, no scheme/port/trailing dot. Fail fast with a clear message.
- **Machine-parseable result line** (last line on stdout, both success and failure), same convention adopted by every entry-point script this cycle:

```
VOIPBIN_INIT: status=ok mode=external domain=example.com tls=byo next="sudo ./scripts/setup-host.sh"
VOIPBIN_INIT: status=error reason="--mode external requires --domain"
```

Exit codes: 0 success, 1 validation/user error, 2 environment error. `start.sh`, `setup-host.sh`, and `check-install.sh` (§2.8) emit the analogous `VOIPBIN_START:`, `VOIPBIN_SETUP_HOST:`, `VOIPBIN_CHECK:` lines.

### 2.3 CoreDNS becomes a compose profile; resolv.conf skipped in external mode

- `docker-compose.yml`: the `coredns` service gets `profiles: ["internal-dns"]`.
- Mode `internal` `.env` contains `COMPOSE_PROFILES=internal-dns`, so every existing command (`docker compose up -d`, `ps`, `start.sh`) behaves exactly as today — Compose reads `COMPOSE_PROFILES` from the project `.env` file.
- Mode `external` `.env` omits the profile: `docker compose up -d` never creates the coredns container, and `docker compose ps -q` counts 47 services instead of 48.
- `init.sh` in external mode: skips Corefile generation and never calls `setup-dns.sh`.
- `setup-dns.sh`, `stop.sh:restore_dns`, `clean.sh --dns`: each reads `DOMAIN_MODE` from `.env` (helper `get_env_var` in `common.sh`) and becomes an explicit no-op in external mode (`log_info "external mode: DNS is operator-managed, skipping"`), not an error. `setup-dns.sh` invoked directly in external mode exits 0 with the same message.
- Test-harness interaction, stated precisely: `t_infra.sh` runs Compose from the project directory, so it reads the same `.env` — on a mode-1 tree `COMPOSE_PROFILES=internal-dns` **is** active in the test project, and coredns's profiles merge to the union `["internal-dns","host-mutating"]`, which would enable it. `t_infra.sh` is unaffected in practice only because it names its services explicitly (`up -d db redis rabbitmq`). To make the isolation guarantee structural rather than incidental, `_gen_test_override.py` emits `profiles: !override ["host-mutating"]` for coredns. Verified as part of the test plan.

### 2.4 Mode-gating the clobber sites

- `common.sh:update_env_ips()`: rewrite `API_URL`/`WEBSOCKET_URL` from `BASE_DOMAIN` read out of `.env` instead of the hardcoded literal (correct in both modes), and skip the rewrite entirely in external mode — in external mode URLs never embed IPs and IP changes don't affect them. `HOST_EXTERNAL_IP`/`KAMAILIO_EXTERNAL_IP`/`RTPENGINE_EXTERNAL_IP` updates still apply in both modes.
- `common.sh:regenerate_ssl_certs()` and the `start.sh` mkcert issuer check + `certs/` wipe: hard-gated to `TLS_MODE != byo`. In external mode `start.sh` must never install mkcert, never inspect issuers, never delete `certs/`. A missing/expired cert in external mode is a fail-fast error naming `install-certs.sh` (§2.6), never an auto-regeneration.
- `start.sh` IP-change regeneration path (`start.sh:617` → `common.sh:regenerate_ip_config`, whose body contains another unconditional `generate_coredns_config` at `common.sh:254`): the destructive inner calls (`update_env_ips`, `regenerate_ssl_certs`) are covered by the choke-point gates above; the Corefile write at `common.sh:254` gets an internal-mode gate for hygiene (it is inert in external mode — coredns is not deployed — but writing `.test` zones onto an external tree is confusing residue). External mode logs that operator DNS may need updating if `HOST_EXTERNAL_IP` changed and continues. (`init.sh:32`'s Corefile call site is covered by §2.3's init-skips-Corefile rule.)
- `setup-voip-network.sh:136-154` (the third clobber site, §1.2): its `update_env_ips`/`regenerate_ssl_certs` calls are covered by the choke-point gates above; its unconditional `generate_coredns_config` (line 150) gets an explicit internal-mode gate, since this script runs in both modes under `setup-host.sh`.
- `start.sh` Steps 7–8 (the fourth clobber site, §1.2): the per-start `generate_coredns_config` call (`start.sh:648-656`) and the `setup-dns.sh -y` invocation (`start.sh:661-668`) are skipped entirely in external mode with a one-line "DNS is operator-managed" log — gated at the call sites, not merely absorbed by the downstream no-ops, so external mode never rewrites `config/coredns/Corefile` and never emits internal-mode DNS messaging.

### 2.5 Sudo isolation: `setup-host.sh` (the one sudo command)

New root-required script `scripts/setup-host.sh` that owns every host mutation, mode-aware (reads `.env`, which must exist — init first):

| Step | internal | external |
|---|---|---|
| Install mkcert package (`apt`/`brew`) + `mkcert -install` (trust store) | yes (if missing) | no |
| Generate/refresh Corefile + `setup-dns.sh -y` (resolv.conf) | yes | no |
| `setup-voip-network.sh` (kamailio/rtpengine macvlan interfaces) | yes | yes |

Idempotent; each step detects "already done" and skips. Emits `VOIPBIN_SETUP_HOST: status=ok mode=<m> steps=<done-list>`.

Correctness details this script owns:

- **CAROOT handoff.** Under `sudo`, `mkcert -install` would resolve `CAROOT` to root's directory and install a *different* CA than the one the unprivileged `init.sh` used to sign the certs — trust would silently never attach. `setup-host.sh` therefore resolves the invoking user's CAROOT explicitly (`CAROOT="$(sudo -u "$SUDO_USER" -H mkcert -CAROOT)"`) and installs in two passes: once as root for the system store, and once as the invoking user (`sudo -u "$SUDO_USER" -H env CAROOT=... mkcert -install`) for the user's NSS store (Chrome/Firefox) — a root-only pass would write root's `~/.pki/nssdb` and leave the user's browsers untrusting. `check-install.sh` (§2.8) independently asserts the issuer chain, so a violation is caught, not masked.
- **Trust installation lives here exclusively.** Two inline escalation sites are removed from the other scripts: the two escalation sites inside `start.sh:setup_mkcert()` — `start.sh:106` (`sudo apt install -y mkcert`) and `start.sh:124-126` (`mkcert -install`) — are removed and replaced by a presence check that fails fast pointing at `setup-host.sh`; the issuer check (`:135-145`) and regeneration branch (`:149`) **remain in the function**, gated per §2.4 (`TLS_MODE != byo`), which is what keeps a `selfsigned` install upgradeable to mkcert on a later start — and `init.sh:186`'s `setup_mkcert_ca` (`mkcert -install`, which self-escalates with sudo when not root and would hang the non-interactive `--yes` flow on a password prompt) runs **only on the root convenience path**. Unprivileged `init.sh` generates certs only; mkcert creates the CA in `$CAROOT` implicitly on first cert generation, and trust installation happens later in `setup-host.sh`. (`start.sh:677`'s `sudo setup-voip-network.sh` also becomes unreachable on the unprivileged path — the prerequisite check fails fast before it.)
- **Ownership.** When the root convenience path is used (`sudo ./scripts/init.sh`), init chowns `.env`, `certs/`, and `config/` to `$SUDO_USER` before exiting, so a later unprivileged `start.sh`/`install-certs.sh` doesn't hit root-owned files.

The supported flows become:

```
# Human-driven (unchanged UX, both modes):
sudo ./scripts/init.sh [flags]   # root path still performs host setup inline, as today
sudo ./scripts/start.sh

# AI-driven (new, both modes):
./scripts/init.sh --mode ... --yes        # unprivileged
sudo ./scripts/setup-host.sh              # the single human-executed sudo command
./scripts/start.sh                        # unprivileged
./scripts/check-install.sh                # unprivileged self-verification
```

Concretely:

- `init.sh`: `check_root` is removed. When run as root it behaves exactly as today (host setup inline at the end). When run unprivileged it performs all unprivileged steps (`.env`, certs — mkcert cert *generation* needs no root; the CA created in `$CAROOT` is trusted later by `setup-host.sh`'s `mkcert -install` — Corefile, gcp creds) and its result line points at `setup-host.sh` as `next`.
- **Legacy `.env` handling:** a `.env` predating this cycle has neither `DOMAIN_MODE` nor `COMPOSE_PROFILES`; naively composing against it would skip coredns while `/etc/resolv.conf` still points at 127.0.0.1 — host-wide DNS breakage on exactly the machines that have existing installs. Rule: `get_env_var DOMAIN_MODE` empty ⇒ treated as `internal` everywhere, and `start.sh`/`check-install.sh` fail fast in internal mode when `COMPOSE_PROFILES` is absent from `.env`, with `reason="stale .env, re-run ./scripts/init.sh --yes"`.
- `start.sh`: `check_root` is replaced by a prerequisite check: VoIP interfaces present (`ip link show kamailio-int`), and in internal mode resolv.conf/CoreDNS reachable. Run as root with prerequisites missing → performs host setup inline (today's behavior). Run unprivileged with prerequisites missing → fail fast with `VOIPBIN_START: status=error reason="host setup missing" next="sudo ./scripts/setup-host.sh"`. Run unprivileged with prerequisites satisfied → proceeds (docker via group membership).
- `stop.sh`/`clean.sh` keep their existing soft-sudo behavior; in external mode their DNS steps are no-ops (§2.3).
- `init_no_sudo.sh` (untracked) is superseded by this design and will not be committed; `check-env-template-sync.sh`'s script array keeps ignoring missing files.

### 2.6 TLS in external mode: BYO with a Let's Encrypt recipe and a renewal hook

Scope decision: **BYO certificate is the supported mechanism; Let's Encrypt is a documented recipe that produces the BYO inputs.** No ACME client is embedded in the sandbox this cycle (renewal automation beyond the install hook is Track B; recorded in §7).

New script `scripts/install-certs.sh <fullchain.pem> <privkey.pem>` (unprivileged, idempotent, usable as a certbot `--deploy-hook`):

1. Validates: key matches cert; cert covers **every name it will be installed for** — `api.<d>`, `sip.<d>`, `sip-service.<d>`, `conference.<d>`, `trunk.<d>`, `registrar.<d>` (SAN check against `BASE_DOMAIN` from `.env`; a non-wildcard cert missing any of these is a hard fail, since kamailio would otherwise fail TLS silently at runtime); warns if expiry < 30 days; warns if `*.registrar.<d>` is not covered (needed only by SIP devices that resolve the realm domain directly instead of using the outbound proxy `sip.<d>`).
2. Installs to the layout kamailio and the scripts already consume: `certs/api/{cert.pem,privkey.pem}` plus `certs/{registrar,conference,sip,sip-service,trunk}.<d>/{fullchain.pem,privkey.pem}` (same cert copied; the wildcard covers all first-level names).
3. Rewrites the four base64 values in `.env` (`API_SSL_*`, `HOOK_SSL_*`).
4. If the stack is running: recreates `api-manager` and `hook-manager` (env-baked certs) and restarts `kamailio` (file-mounted certs). If not running: skips with a note.
5. Emits `VOIPBIN_CERTS: status=ok domain=<d> expires=<date>`.

**Renewal runs as root; ownership must survive it.** The documented certbot `--deploy-hook` executes `install-certs.sh` as root. The script therefore preserves the pre-existing owner/group/mode of `.env` and of everything it writes under `certs/` (capture with `stat` before, restore after — or edit in place without replacing the inode); paths it newly creates inherit the owner/group of the `certs/` directory itself. So the next unprivileged `start.sh` (`sed -i` on `.env`) does not die on root-owned files.

`init.sh --tls byo --cert F --key K` runs the step-1 validation as a **pre-flight against the `--domain` argument, before `.env` is written** (so a bad cert aborts init cleanly with no half-written `.env`), then calls `install-certs.sh` for steps 2–3, and **skips its own cert generation entirely** — the Step-3 `generate_cert` loop (`init.sh:208`) and Step-4 `generate_api_cert` (`init.sh:215`) do not run in external mode, so no stale `certs/*.voipbin.test/` directories are created and the BYO base64 values are never overwritten by a self-signed cert.

Documented Let's Encrypt recipe (README/runbook): a wildcard needs DNS-01 —

```
certbot certonly --preferred-challenges dns --manual \
  -d example.com -d '*.example.com' -d '*.registrar.example.com'
# renewal: certbot renew --deploy-hook '/path/to/sandbox/scripts/install-certs.sh \
#   /etc/letsencrypt/live/example.com/fullchain.pem /etc/letsencrypt/live/example.com/privkey.pem'
```

(with a note that DNS-provider certbot plugins make this non-interactive, and that HTTP-01 cannot issue wildcards).

### 2.7 Domain-in-state caveat: refuse mode/domain switches, document the escape hatch

`init.sh`, when `.env` already exists, compares requested (`mode`, `domain`) against the existing `DOMAIN_MODE`/`BASE_DOMAIN`:

- Same mode+domain → normal overwrite/refresh semantics (prompt, or `--yes`).
- Different → **refuse** with exit 1 and an explanation: extension SIP realms embed the domain in the database; switching requires wiping or regenerating state. The message names the two supported escape hatches:
  1. Full reset: `./scripts/clean.sh --volumes --purge` then re-init — the clean path for demo installs. (`--purge` alone removes `.env`/certs but **keeps the DB volume with the old-domain realms** — the worst state; the message and docs always show the combined form. Today `clean.sh` does not touch the `.test_data_initialized` marker at all; **this cycle extends `clean.sh --volumes` to remove it**, so `start.sh:694` re-seeds the test customer against the new domain instead of skipping.)
  2. `--force-reinit`: rewrites `.env`/certs/Corefile for the new domain, prints the exact follow-up required for live state (delete + recreate extensions via API, e.g. `setup_test_customer.sh` for the test customer; recreate `registrar-manager`, `api-manager`, `hook-manager`, `customer-manager`, `square-*` containers), and does **not** touch the database itself.

**Host-state teardown on internal→external switch.** Rewriting `.env` is not enough: the `voipbin-dns` container would be orphaned (once `COMPOSE_PROFILES` drops `internal-dns`, `docker compose down` no longer manages it, and it keeps holding port 53), and `/etc/resolv.conf` would stay hijacked — which `check-install.sh`'s external-mode resolv.conf check would then rightly fail. `--force-reinit` from internal to external therefore *precondition-checks* host state and refuses with the exact commands if any remain: stack down under the old `.env` (`docker compose down`, which still includes the profile and removes coredns), then `sudo ./scripts/setup-dns.sh --uninstall` (restores resolv.conf, removes the backup). Only a clean host proceeds.

The caveat (mode selection is an init-time decision; what "switching later" costs) is documented in README and CLAUDE.md.

### 2.8 Mode-aware post-install smoke check: `check-install.sh`

New unprivileged script an agent (or human) runs to self-verify, replacing "eyeball the start.sh summary":

| Check | internal | external |
|---|---|---|
| Service count: `docker compose ps` running == `docker compose config --services \| wc -l` under the active profile set (derived, not hardcoded — self-maintaining as services are added; implementation note: this hinges on both commands applying the same profile filter, so both are invoked with the identical environment and the `.env`-sourced `COMPOSE_PROFILES`), none unhealthy/restarting/exited | ✓ | ✓ |
| Cert trust chain: issuer of `certs/api/cert.pem` is the mkcert CA actually installed in the trust store (catches the CAROOT-mismatch failure, §2.5) | ✓ | n/a (real-CA check below) |
| DNS: `api.<d>` and `sip.<d>` resolve to `HOST_EXTERNAL_IP` / `KAMAILIO_EXTERNAL_IP` | via `dig @127.0.0.1` | via system resolver; mismatch = fail, listing expected records |
| TLS: `curl https://api.<d>:8443/ping` | with mkcert CA / `-k` fallback | **without `-k`** — chain must validate; cert expiry > 14 days |
| API liveness: `/ping` responds | ✓ | ✓ |
| Realm config sanity: running registrar-manager's `DOMAIN_NAME_EXTENSION` == `.env` value (`docker inspect`) | ✓ | ✓ |
| resolv.conf state matches mode (internal: 127.0.0.1; external: untouched, no `.voipbin-backup` expected) | ✓ | ✓ |

Output: one `CHECK <name>: pass|fail|skip <detail>` line per check, final `VOIPBIN_CHECK: status=pass|fail passed=N failed=M mode=<m>`; exit 0 only if all pass. SIP registration/call verification stays in the existing `test_call.py`/`softphone.py` tools (which gain `--domain`/env-derived defaults, §2.10) — `check-install.sh` stays network-service-level so it is safe to run anywhere.

### 2.9 Operator DNS runbook (external mode)

New README section (mirrored in CLAUDE.md), the operator-facing equivalent of what the install repo does with Terraform:

| Record | Type | Target | Purpose |
|---|---|---|---|
| `api.<d>` | A | Host IP | REST API + WebSocket (:8443) |
| `admin.<d>` / `meet.<d>` / `talk.<d>` | A | Host IP | Web UIs (:3003/:3004/:3005) |
| `sip.<d>` | A | Kamailio external IP | SIP signaling / WSS (:5060/:5066) |
| `sip-service.<d>`, `conference.<d>`, `trunk.<d>`, `pstn.<d>` | A | Kamailio external IP | SIP surfaces |
| `registrar.<d>` | A | Kamailio external IP | Apex registrar name — passed to `square-admin`/`square-talk` as `REGISTRAR_DOMAIN` and asserted by today's DNS test; **not** covered by the wildcard below |
| `*.registrar.<d>` | A | Kamailio external IP | Per-customer SIP realm resolution (devices resolving the realm domain directly) |

Plus: TTL guidance; the explicit statement that `HOST_EXTERNAL_IP` and `KAMAILIO_EXTERNAL_IP` are two distinct addresses on the same subnet (macvlan), so the deployment environment must route both — **directly-routable environments (on-prem, corporate LAN with internal DNS, cloud with multiple routable IPs) are the supported target for external mode this cycle; single-public-IP NAT environments (typical cloud VM) are a documented limitation** carried as a follow-up (§7), because collapsing Kamailio onto the host IP is a networking redesign, not a DNS one: kamailio runs `network_mode: host` and binds `KAMAILIO_EXTERNAL_LB_ADDR` (the macvlan address) directly for SIP/TLS listening — there is no port mapping to remap.

> **Acceptance-criteria amendment (explicit, for the ticket owner):** this narrows the ticket's "fresh install in mode 2 on a host with a real domain" to *directly-routable* hosts. A single-public-IP cloud VM — a likely AI-driven install target — is out of scope until the NAT follow-up lands. Flagged in the review report rather than buried here.

**Cleartext web UIs, stated honestly:** the `admin`/`meet`/`talk` UIs are served over plain HTTP on :3003–:3005 in both modes today. On a real, possibly routable domain this means login credentials/JWTs in the clear. The runbook says so explicitly and recommends fronting the UIs with a TLS reverse proxy or restricting them to trusted networks; UI TLS termination itself is a §7 follow-up alongside the port-443 item.

### 2.10 CLI and SIP test tooling: minimal mode-awareness

Full de-hardcoding of `voipbin-cli.py` (30+ sites) is out of scope. In scope, because they would otherwise lie to the operator or break:

- `status` / `info` / `open`: read `BASE_DOMAIN` from `.env` when composing URLs.
- `dns` subcommands (`status`/`list`/`setup`/`test`/`regenerate`): in external mode, print "DNS is operator-managed in external mode" plus the §2.9 record table (with actual domain/IPs substituted) and exit 0.
- `certs` subcommands (`status`/`trust`): today they advise `rm -rf certs/` + re-init — destructive to a BYO install. In external mode they report cert expiry/SANs and point at `install-certs.sh` instead.
- `clean --dns`: no-op in external mode (§2.3). `clean --volumes` (CLI) and `clean.sh --volumes` both remove `.test_data_initialized` — the marker semantics are aligned across the two implementations (today the CLI removes it under `--purge`, the shell script never does; both move to `--volumes`, where the DB state it mirrors actually lives; implementation note: in `voipbin-cli.py` the marker sits inside the single purge-gated `files_to_remove` list, so the change lifts that one entry out — not a re-gating of the whole list).
- `test_call.py` / `softphone.py`: derive server and realm-domain defaults from `.env` (`sip.<BASE_DOMAIN>`, `{cid}.<DOMAIN_NAME_EXTENSION>`) instead of hardcoded `voipbin.test`; explicit CLI args still override.

Remaining cosmetic literals in CLI help/reference text are annotated as internal-mode examples.

## 5. Non-goals

- No embedded ACME client / automatic renewal daemon (documented certbot deploy-hook instead) — Track B TLS lifecycle remains open beyond the install hook.
- No port-443 migration for external mode (stays :8443/:3003-3005).
- No NAT/single-public-IP support for external mode (documented limitation, §2.9).
- No in-place domain migration of DB state (refuse + documented escape hatches, §2.7).
- No full de-hardcoding of `voipbin-cli.py` beyond §2.10.
- No CI wiring (unchanged from the parity cycle's deferral).
- No changes to the monorepo/install repo.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Mode-1 regression from `start.sh`/`init.sh` restructure (the highest-value invariant) | Byte-exact `.env` derivation test; root-path behavior preserved verbatim (root run == today's flow); live internal-mode verification before merge (§4) |
| `COMPOSE_PROFILES` in the operator's shell env overriding `.env` (shell wins in Compose precedence) | `start.sh`/`check-install.sh` detect a shell-set `COMPOSE_PROFILES` that contradicts the mode and fail fast — the check runs at the top of `main()`, **before** `start.sh:240`'s `set -a; source .env` overwrites the shell value and hides the conflict |
| Real-CA certs destroyed by legacy mkcert auto-regen paths reached through an untouched entry point | Gate lives in `common.sh:regenerate_ssl_certs` itself (the shared choke point), not only in callers; `TLS_MODE=byo` makes it refuse |
| `install-certs.sh` base64 rewrite corrupting `.env` | Write via temp file + atomic move; bats-covered |
| bats suite asserting old literals breaks | Assertions updated with the change, per phase, suite green at each commit |
| External-mode live verification environment not immediately available | Explicitly tracked as the Done gate (§4); everything below it is testable without it |
